# FF3 monsters — the measured fields

Generated by `tools/ff3-monster-catalog.mjs`. Pinned by
`tools/check-ff3-monsters.mjs`, which fights a real Goblin for every claim.

`tools/gen-monsters-js.js` already built `src/data/monsters.js` from these
tables, but its header credited "Data Crystal ROM map" — a secondary source.
This project's rule is that the ROM beats a wiki, so the layout was put in
front of the running game the way FF1's and FF2's were.

## The tables

| table | file offset | shape |
|---|---|---|
| monster properties | `0x60010` | 16 bytes per bestiary id |
| stat entries | `0x61010` | 3 bytes per entry, indexed BY the record |
| gil | `0x61c68` | 2 bytes LE per id |

Tracing an actual encounter and mapping every cartridge read back to a file
offset shows the game reading exactly these addresses. That is a measurement,
not a citation.

## What was measured

**HP** is properties `+1`/`+2`. Patching it to 300 and then 400 puts exactly
those values into the enemy block in RAM.

**ATTACK** is byte 2 of the stat entry that properties `+9` points at. Patching it to 0 and then 255
moves the damage the party TAKES from 34 to 118.

**DEFENCE** (byte 2) and **EVADE** (byte 0) share the entry properties `+12` points at.
Both cut the damage the party deals, so "damage fell" pins neither. They
separate on the same signature FF1's do — **evasion drives damage to ZERO,
defence FLOORS it above zero** (Goblin, entry `[0,10,1]`):

```
byte 0 = 0/32/64/128/192/255  ->  99  0  0  0  0  0     floor ZERO
byte 2 = 0/32/64/128/192/255  -> 111 12 12 12 12 12     floor TWELVE
```

and the battle text settles it outright. At byte 0 = 255 the screen prints
**"Miss" ×26**, a word that appears nowhere at baseline or with defence maxed.
At byte 2 = 255 the hit counts are identical to baseline (`1xHit ×28,
`2xHit ×12`, `3xHit ×2`) and only the damage collapses. Byte 0 makes the party
miss; byte 2 lets them land and soaks it.

## ⛔ What was retracted

`$7678` **is not the monster's current HP.** It is a copy HP is loaded into
that never moves again. An earlier pass measured damage there, read "0 dealt"
every time, and concluded the party simply could not hurt a Goblin — so
defence and evade were reported as unverifiable. Patching HP to 500 and
scanning every address holding it:

```
$7678: 500 -> 500     $76B8: 500 -> 485   <-- the only one that moves
$767A: 500 -> 500     $76BA: 500 -> 500
```

Current HP is `$76B8`; `$76BA` is the max beside it.
The lesson: an address that merely **holds** the right value at battle start
has not been shown to be the live one — make it move first.

Byte 1 of the defence entry (Goblin's natural 10) does nothing measurable —
0 and 255 both leave the damage at exactly 99, on a measurement sensitive
enough to catch both of its neighbours. It is left unnamed rather than guessed.

Everything else in the 16-byte record (level, spAtkRate, weakness, spirit,
atkElem, statusOnAtk, elemResist, statusResist, spAtkIdx) is **inherited from
Data Crystal, not measured.** Do not cite it as verified.
